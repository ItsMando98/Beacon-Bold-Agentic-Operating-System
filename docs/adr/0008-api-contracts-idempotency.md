# ADR 0008: Vertragsgebundene API und atomare Idempotenz

Status: P1-3 implementiert; Authentifizierung und Audit bleiben P1-4/P1-6.

P1-1 ist als PR #9 und P1-2 als PR #10 regulär gemergt. P1-7 / PR #11 wurde nach Auflösung des Lockfile-Konflikts und erneuten neun erfolgreichen Pflichtprüfungen regulär gemergt. Dieser Aufgaben-Branch startet von main `67311b56f5231128a1d1333436f9bb81faa7f646`. Gate 0 bleibt durch die dokumentierten VPS-, HTTPS- und Backup-/Restore-Nachweise erfüllt.

Hono wird durch `@hono/zod-openapi` 1.6.3 erweitert. Die Routen übernehmen die vorhandenen Zod-Eingabe-/Ausgabeverträge aus `packages/schemas`; HTTP-spezifische Header-, Kommando-, Speicher- und Dokumentationsverträge kommen in `src/http.ts` dazu. Der bestehende Generator bleibt Quelle von `/openapi.json`. HTTP-Header werden nur für REST ergänzt und gelangen nicht als fachliche Eingabe in MCP-Tools. Der Contract-Test vergleicht sämtliche tatsächlich registrierten GET-/POST-Routen mit dem generierten Dokument und validiert ihre realen Antworten. Es gibt keine separat gepflegten fachlichen Eingabe- oder Ausgabetypen.

Die API stellt GET /health, POST /customers, GET /openapi.json, GET /docs und GET /docs/scalar.js bereit. Jede Anfrage erhält eine serverseitige UUID in X-Request-Id. Fehler verwenden ausschließlich den gemeinsamen ApiError-Vertrag einschließlich dieser UUID. Validierungsfehler werden 400, fehlende Identität 401, eine widersprüchliche Schlüsselwiederverwendung 409 und unbekannte Routen 404. Unerwartete Fehler werden 500 ohne interne Meldungen oder SQL-/Konfigurationswerte. Scope-Durchsetzung und Token-Prüfung bleiben P1-4.

POST /customers erfordert einen Idempotency-Key aus 8 bis 128 ASCII-Zeichen (Buchstaben, Ziffern, Punkt, Unterstrich, Doppelpunkt, Bindestrich). Der Schlüssel ist zusammen mit Mandant und Operation eindeutig. Hashbasis ist die normalisierte, validierte Eingabe. Eine gleiche Anfrage liefert die ursprüngliche 201-Antwort samt identischer Kunden-ID und Zeitstempel; eine andere Eingabe mit demselben Schlüssel erhält 409. Ungültige Anfragen reservieren keinen Schlüssel.

Die PostgreSQL-Implementierung liegt im Datenpaket, Verbindungen ausschließlich im Adapter `packages/integrations/src/api.ts`. Innerhalb von withTenant wird ein transaktionsgebundener Advisory Lock auf Mandant/Operation/Schlüssel genommen. Kundenanlage und gespeicherte Antwort werden atomar committed. Bei einem Fehler wird beides zurückgerollt. Ein konkurrierender identischer Aufruf wartet und liest danach die gespeicherte Antwort. Lock-Wartezeit ist auf fünf Sekunden begrenzt; ein Überschreiten läuft als maskierter 500-Fehler aus und die Anfrage darf wiederholt werden. Hash-Kollisionen des Sperrschlüssels können nur zusätzliche Serialisierung verursachen, keine gemeinsamen Datensätze: Der tatsächliche Primärschlüssel enthält die ungekürzten Werte.

Die Vorwärtsmigration `0003_idempotency.sql` ergänzt einen schema-abgeleiteten Snapshot für den Idempotenzspeicher. Sie erzwingt ENABLE/FORCE RLS, eine Mandantenreferenz und lediglich SELECT/INSERT für beacon_app. Bestehende Migrationen bleiben unverändert. Tests beweisen leeren Zugriff ohne Mandantenkontext, fremden Schreibabbruch, unveränderbare Antworten, Kontextbereinigung und vollständigen Rollback bei einer gezielt ausgelösten Speicherstörung.

Im Entwicklungs-/Mock-Server gilt ausschließlich der feste erfundene Mandant aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa mit einem flüchtigen Speicheradapter. Im Live-Server ist kein Identitätsresolver konfiguriert, daher werden alle Kunden-Schreibzugriffe geschlossen mit 401 abgewiesen. Öffentliche Tenant-Header werden niemals vertraut. Für Tests und spätere P1-4-Integration existiert ein intern injizierter Resolver; er ist kein öffentlicher Auth-Ersatz. Der PostgreSQL-Pool wird beim Stoppen geschlossen.

Scalar 0.12.8 verwendet die lokal gebündelte Browserbibliothek 1.72.3. Telemetrie und externe Standardschriften sind deaktiviert. Der Browser-Test blockiert Drittanbieterabrufe und prüft sichtbare Dokumentation, lokale Assets, gültiges OpenAPI sowie eine Kundenanlage mit Wiederholung gegen die gebaute API. Das Bundle enthält seine Browserbibliothek, sodass die vorhandenen Runtime-Images keine neuen Dateikopien benötigen. CommonJS-Abhängigkeiten wie pg erhalten im ESM-Bundle eine Node-createRequire-Brücke; die tatsächliche Startabnahme prüft das Ergebnis.

Offene Entscheidungen: Auth-Provider und Agenten-Token/Scopes (P1-4), automatische Audit-/Notbremsenprüfung (P1-6), fachliche Kundenfelder und öffentliche API-Versionierung. Der Idempotenzspeicher behält Antworten dauerhaft; Aufbewahrungsdauer und kontrollierte Bereinigung benötigen eine spätere Betreiber-/Datenschutzentscheidung. Dieser PR legt dafür keine Frist fest und löscht keine historischen Antworten. P1-8 bleibt offen, neue Geldwirkungen benötigen die bestehende konkrete manuelle Gründerfreigabe.

Keine Produktion, AWS-Provisionierung oder Bereitstellung neuer VPS-Dienste. Vor einem späteren Staging-Start muss die neue Vorwärtsmigration wie bisher vor dem Anwendungsstart laufen. Der bestehende begrenzte Merge-Deploy bleibt erhalten; der Entwurfs-PR selbst deployt nicht.
